# Docker

У всех нас совершенно разные операционные системы: кто-то предпочитает универсальность Windows, кому-то нравится экосистема macOS. Возможно, среди вас есть и отъявленные линуксоиды.

В разных системах мы пользуемся разными менеджерами пакетов, например choco, brew или apt. Способы установки программ и исполняемые файлы тоже могут отличаться.

А еще у каждого могут быть свои предпочтения в средах разработки!

Как же тогда сделать так, чтобы проект работал у каждого на машине одинаково?

Ответ прост — Docker. С помощью этого дружелюбного синего китенка мы можем упаковать наш проект таким образом, чтобы запускать его в одинаковом окружении на разных компьютерах с Docker :)

# Три сущности Docker

Три столпа, на которых держится Docker, — это Dockerfile, образ и контейнер.

Допустим, мы написали скрипт на Python и хотим, чтобы у преподавателя он запустился в том же окружении. В **Dockerfile** укажем, какой взять базовый образ, что установить и какие файлы скопировать.

По этим инструкциям Docker соберёт _**образ**_ (англ. image). В нашем примере в нём будут Python, нужные библиотеки и сам скрипт. Готовый образ можно передать или выложить в Docker Hub.

Когда мы запускаем образ, Docker создаёт _**контейнер**_. Именно в нём выполняется скрипт. Из одного образа можно запустить несколько контейнеров.

# Пишем Dockerfile

## Что уже есть

Ваш преподаватель по линейной алгебре задал вам решить систему уравнений, поэтому вы решили написать Python-скрипт, который сделает это за вас. У преподавателя другая операционная система, но Docker у него уже установлен.

Ваш проект выглядит так:

```bash
my-project
├── requirements.txt
└── solve-equations.py
```

У `requirements.txt` наполнение следующее:

```txt
rich # пакет для красивого вывода в терминал
numpy # полезная библиотека для выполнения вычислений
```

В файлике `solve-equations.py` написано это:

```py
import numpy as np
from rich.console import Console
from rich.table import Table

A = np.array([[1, 1], [1, -1]])
b = np.array([6, 2])

# Матрицей A и вектором b кодируем систему уравнений
# x + y = 6
# x - y = 2

x, y = np.linalg.solve(A, b) # нампи, дай нам решения пожалуйста

table = Table(title="Решение системы уравнений")
table.add_column("Переменная", style="cyan")
table.add_column("Значение", style="green")

table.add_row("x", str(x))
table.add_row("y", str(y))

Console().print(table)
```

> [!NOTE] Читать код совсем необязательно, главное — знать, что он работает :)

## Заворачиваем в образ

Создадим `Dockerfile` там же, где и проект:

```bash
my-project
├── Dockerfile
├── requirements.txt
└── solve-equations.py
```

### FROM

Для начала выберем образ, на котором будем базироваться. Нам подойдёт официальный образ Ubuntu 22.04 (Jammy Jellyfish, "везучая медуза").
В Dockerfile укажем базовый образ одним из двух способов.

```Dockerfile
FROM ubuntu:22.04
# Или: FROM ubuntu:jammy
```

### WORKDIR

Выберем рабочую директорию (папку) внутри контейнера. Для удобства возьмём `/app`. Последующие команды будут запускаться из неё, а относительные пути внутри контейнера будут отсчитываться от неё. Из раздела про Linux мы помним, что `.` — текущая директория, а `..` — директория уровнем выше.

Зададим `/app` в Dockerfile:

```Dockerfile
WORKDIR /app
```

### RUN 1/2

Инструкция `RUN` позволяет запускать терминальные команды _**во время сборки образа**_.
Попросим Docker запустить команду:

```Dockerfile
RUN apt-get update && \
    apt-get install -y python3 python3-pip
```

Мы просим `apt-get` обновить списки пакетов и затем установить Python и pip.
Зачем такой громоздкий синтаксис? Почему бы не написать так?

```Dockerfile
RUN apt-get update
RUN apt-get install -y python3 python3-pip
```

Дело в том, что Docker собирает образы _по слоям_ и может использовать результаты прошлой сборки из кэша. Если поменять список устанавливаемых пакетов во втором `RUN`, Docker может заново запустить установку со старыми списками из первого `RUN`. Когда обе команды в одном `RUN`, списки обновляются вместе с установкой.

> [!NOTE]
> Если создать большой файл в одном `RUN`, а в следующем удалить, в итоговой файловой системе вы его не найдёте. При этом файл всё ещё занимает место в предыдущем слое образа.

### COPY 1/2

Скопируем файлы из нашего проекта в образ. Вспомните, что теперь наша рабочая директория — `/app`, поэтому для обращения к ней мы используем `.`!

```Dockerfile
COPY requirements.txt .
```

### RUN 2/2

На этом этапе попросим pip установить в системный Python пакеты, которые мы добавили:

```Dockerfile
RUN pip3 install --no-cache-dir -r requirements.txt
```

### COPY 2/2

Скопируем основной Python-файл:

```Dockerfile
COPY solve-equations.py .
```

### CMD

Мы добавили все, что надо для запуска. Теперь займемся непосредственно им. `CMD` задаёт команду, которая по умолчанию выполняется при запуске _**контейнера**_. Не перепутайте с `RUN`, который запускается при сборке _**образа**_.
Потребуем запустить наш скрипт:

```Dockerfile
CMD ["python3", "solve-equations.py"]
```

Мы отдаем в `CMD` массив строк. Таким образом, мы можем гибко настраивать аргументы для запуска.

## Итоговый Dockerfile

В итоге получаем вот такой незамысловатый Dockerfile:

```Dockerfile

FROM ubuntu:jammy

WORKDIR /app

RUN apt-get update && \
    apt-get install -y python3 python3-pip

COPY requirements.txt .

RUN pip3 install --no-cache-dir -r requirements.txt

COPY solve-equations.py .

CMD ["python3", "solve-equations.py"]
```

# Управляем контейнерами и образами

Мы написали Dockerfile. А как теперь, собственно, собрать образ?
Для этого существуют терминальные команды, с которыми мы сейчас и разберемся.

> [!NOTE]
> Команды ниже вводим в терминале своего компьютера. На Windows и macOS для этого примера запустите [Docker Desktop](https://www.docker.com/products/docker-desktop/) с Linux-контейнерами. На Linux достаточно запущенного Docker Engine.

Соберем образ:

```bash
docker build -t gauss:1.0 .
```

В `-t` мы передаем имя образа (`gauss`, в честь Карла Фридриха Гаусса, методом которого мы и решаем уравнения) и тег (`1.0`).
`.` указывает, что контекст сборки — текущая папка. В ней Docker по умолчанию ищет Dockerfile, из неё же берёт файлы для `COPY`. Поэтому запускайте эту команду из папки проекта.

После сборки давайте запустим наш контейнер:

```bash
docker run --rm --name my-container gauss:1.0
```

Флаг `--rm` означает, что после завершения работы Docker автоматически удалит контейнер. `--name` просто задает имя контейнера, чтобы к нему можно было обращаться. Вывод должен быть вот таким:

```txt
Решение системы уравнений
┏━━━━━━━━━━━━┳━━━━━━━━━━┓
┃ Переменная ┃ Значение ┃
┡━━━━━━━━━━━━╇━━━━━━━━━━┩
│ x          │ 4.0      │
│ y          │ 2.0      │
└────────────┴──────────┘
```

При запуске контейнера можем указать свою команду вместо той, что в `CMD`. Например, запустим `bash` — командную оболочку, или шелл (shell). В ней можно тренироваться запускать команды из раздела про Linux.

```bash
docker run --rm -it gauss:1.0 /bin/bash
```

Мы указываем _абсолютный_ путь к bash внутри контейнера — `/bin/bash`. Флаг `-i` держит открытым стандартный ввод (`stdin`), а `-t` выделяет псевдотерминал. Вместе они позволяют работать в оболочке интерактивно.

Если вы хотите сохранить контейнер для дальнейшего использования, запустите его без `--rm` и дайте ему имя.

```bash
docker run -it --name gauss-shell gauss:1.0 /bin/bash
```

После выхода из bash через `exit` вы сможете увидеть остановленный контейнер в списке.

```bash
docker ps -a
```

`-a` значит a[ll]. Не указав этот флаг, вы получите список активно запущенных (но не остановленных) контейнеров.

Запустить остановленный контейнер можно командой:

```bash
docker start -ai gauss-shell
```

`-a` подключает вывод контейнера к вашему терминалу, а `-i` — ввод. Docker снова запустит `bash` в том же контейнере, и вы окажетесь в его оболочке.

## Volume

Когда мы удаляем контейнер, изменения в его собственной файловой системе пропадают. Чтобы сохранить данные между запусками, можно подключить **том** Docker.

```bash
docker run --rm -v gauss-data:/gauss-data:ro gauss:1.0
```

`gauss-data` — имя тома, которым управляет Docker. `/gauss-data` — путь, по которому том будет доступен внутри контейнера. Суффикс `:ro` означает «только чтение». Если убрать его, контейнер сможет и читать, и записывать данные в том.

Если нужно подключить уже существующую папку проекта, вместо имени тома укажите путь к папке. Например, `-v ./data:/gauss-data:ro` подключит локальную папку `data`.

# Залезаем в контейнер через IDE

Наверняка у вас есть любимая среда разработки или IDE. Поэтому умные люди придумали, как облегчить нам жизнь при работе с контейнерами.

Если у вас Visual Studio Code, установите расширение Dev Containers. Пока контейнер запущен, нажмите <kbd>Ctrl</kbd> + <kbd>Shift</kbd> + <kbd>P</kbd> (или <kbd>Cmd</kbd> вместо <kbd>Ctrl</kbd>, если вы на Mac), выберите **Dev Containers: Attach to Running Container...**, а затем выберите контейнер из списка.
