# Кто такой Docker и с чем его едят
У всех нас совершенно разные операционные системы: кто-то предпочитает универсальность Windows, кому-то нравится экосистема macOS. Возможно, среди вас есть и отъявленные линуксоиды.

У каждой ОС свой менеджер пакетов (примеры: choco, brew и apt), способ установки программ, исполняемые файлы и пр.

А еще у каждого могут быть свои предпочтения в средах разработки!

Как же тогда сделать так, чтобы проект работал у каждого на машине одинаково?

Ответ прост — Docker. С помощью этого дружелюбного синего китенка мы можем упаковать наш проект таким образом, чтобы он запускался на любом компьютере или ноутбуке с установленным Докером :)

# Три сущности Docker
Три столпа, на которых держится Docker, — это Dockerfile, образ и контейнер.

Представим, что вы готовите, скажем, пельмени.
Очевидно, что для приготовления пельменей вам понадобятся тесто, фарш, соль, лавровые листья и кипяток. 
Помимо этого вам нужен рецепт: что и в какой последовательности собирать и варить.

Именно этим рецептом и выступает Dockerfile. Про его структуру мы поговорим в разделе ниже.

Итак, по этому рецепту мы варим громадную партию пельменей, а потом замораживаем их. Эту партию можно кому-то передать, можно скопировать (заморозить еще пельменей) и можно выложить на какой-нибудь сайт (спойлер: Docker Hub). Эта партия называется ***образом***.

Допустим, Василий Пупкин получил пачку замороженных пельменей и решил сварить их себе на ужин. Конкретная порция пельменей, полученная из образа (по образу и подобию, если угодно), называется ***контейнером***. Причем состояние контейнера можно менять, как сваренные пельмени можно приправить сметанкой или кетчупом. А потом эти пельмени с соусом можно заморозить и сделать из них образ!

В общем, цепочка такая: Dockerfile собирает образ (англ. image), который запускает контейнер.
> [!NOTE] Формально контейнер можно назвать изменяемым экземпляром образа.


# Пишем рецепт для контейнера

## Что уже есть

Ваш преподаватель по линейной алгебре задал вам решить систему уравнений, поэтому вы решили написать Python-скрипт, который сделает это за вас. К сожалению, у вашего преподавателя какая-то древняя операционная система, на которой запустится разве что Docker.

Ваш проект выглядит так:
```bash
my-project
├── requirements.txt
└── solve-equations.py
```
У `requirements.txt` наполнение следующее:
```txt
rich # пакет для красивого вывода в терминал
numpy # полезная библиотека для выполнения вычислений
```
В файлике `solve-equations.py` написано это:
```py
import numpy as np
from rich.console import Console
from rich.table import Table

A = np.array([[1, 1], [1, -1]])
b = np.array([6, 2])

# Двумя матрицами выше кодируем систему уравнений
# x + y = 6
# x - y = 2

x, y = np.linalg.solve(A, b) # нампи, дай нам решения пожалуйста

table = Table(title="Решение системы уравнений")
table.add_column("Переменная", style="cyan")
table.add_column("Значение", style="green")

table.add_row("x", str(x))
table.add_row("y", str(y))

Console().print(table)
```
>[!NOTE] Читать код совсем необязательно, главное — знать, что он работает :)

## Заворачиваем в образ
Создадим `Dockerfile` там же, где и проект:
```bash
my-project
├── Dockerfile
├── requirements.txt
└── solve-equations.py
```

### FROM
Для начала выберем образ, на котором будем базироваться. Нам подойдёт официальный образ Ubuntu 22.04 (Jammy Jellyfish, "везучая медуза").
На языке Dockerfile это будет выглядеть так:
```Dockerfile
FROM ubuntu:22.04
# Или
FROM ubuntu:jammy
```

### WORKDIR
Контейнер можно для простоты считать маленькой операционной системой, поэтому нам нужно указать, какая у нас будет рабочая директория (папка). По умолчанию для пользователей в Linux-подобных системах рабочей будет 
`/home/имя-пользователя`, но в нашем случае рабочей будет `/app` для удобства.

Начиная с рабочей директории будет отсчитываться дальнейшая файловая система. О навигации мы поговорим позже в разделе про Linux, но пока можно знать, что `.` — текущая директория, а `..` — директория уровнем выше.

Зададим `/app` в Dockerfile:
```Dockerfile
WORKDIR /app
```

### RUN 1/2
Команда RUN позволяет запускать терминальные команды ***во время сборки контейнера***.
Попросим Docker запустить команду:
```Dockerfile
RUN apt-get update && \
    apt-get install -y python3 python3-pip
```
Мы просим пакетный менеджер aptitude (apt) обновить базу пакетов и затем скачать Python и pip.
Зачем такой громоздкий синтаксис? Почему бы не написать так?
```Dockerfile
RUN apt-get update
RUN apt-get install -y python3 python3-pip
```
Дело в том, что Docker собирает образы *по слоям*. И каждый слой кэшируется ради ускорения сборки. Поэтому во втором случае Docker может закэшировать старую версию пакета.
>[!NOTE] Лучше всего различие видно, если создать через RUN большой файл, а потом его в следующем RUN удалить. В файловой системе вы его не найдете, зато вес этого файла будет учитываться в общем весе контейнера.

### COPY 1/2
Скопируем файлы из нашего проекта в контейнер. Вспомните, что теперь наша рабочая директория — `/app`, поэтому для обращения к ней мы используем `.`!
```Dockerfile
COPY requirements.txt .
```
### RUN 2/2
На этом этапе попросим pip установить в системный Python пакеты, которые мы добавили:
```Dockerfile
RUN pip3 install --no-cache-dir -r requirements.txt
```
### COPY 2/2
Скопируем основной Python-файл:
```Dockerfile
COPY solve-equations.py .
```

### CMD
Мы добавили все, что надо для запуска. Теперь займемся непосредственно им. `CMD` исполняет команду при запуске ***контейнера***. Не перепутайте с `RUN`, который запускается при сборке ***образа***.
Потребуем запустить наш скрипт:
```Dockerfile
CMD ["python3", "solve-equations.py"]
```
Мы отдаем в `CMD` массив строк. Таким образом, мы можем гибко настраивать аргументы для запуска.

## Итоговый рецепт

В итоге получаем вот такой незамысловатый Dockerfile:
```Dockerfile

FROM ubuntu:jammy

WORKDIR /app

RUN apt-get update && \
    apt-get install -y python3 python3-pip

COPY requirements.txt .

RUN pip3 install --no-cache-dir -r requirements.txt

COPY solve-equations.py .

CMD ["python3", "solve-equations.py"]
```

# Управляем контейнерами и образами
Мы создали рецепт создания образа. А как его, собственно, создать?
Для этого существуют терминальные команды, с которыми мы сейчас и разберемся.

>[!NOTE] Для работы вам понадобится запущенное приложение Docker Desktop. Скачайте его [здесь](https://www.docker.com/products/docker-desktop/).

Соберем образ:
```bash
docker build -t gauss:1.0 .
```
В `-t` мы передаем название контейнера (`gauss`, в честь Карла Фридриха Гаусса, методом которого мы и решаем уравнения) и тег (числовой идентификатор, в нашем случае `1.0`). 
`.` — контекст сборки, то есть папка, в которую Docker должен смотреть при сборке. Поэтому команду надо запускать из той же директории, где лежит Dockerfile.

После сборки давайте запустим наш контейнер:
```bash
docker run --rm gauss:1.0 --name my-container
```
Флаг `--rm` означает, что после завершения работы контейнер можно удалить. `--name` просто задает имя контейнера, чтобы к нему можно было обращаться. Вывод должен быть вот таким:
```txt
┏━━━━━━━━━━━━┳━━━━━━━━━━┓
┃ Переменная ┃ Значение ┃
┡━━━━━━━━━━━━╇━━━━━━━━━━┩
│ x          │ 4.0      │
│ y          │ 2.0      │
└────────────┴──────────┘
```
Как уже упоминалось, наш контейнер — маленькая ОС, поэтому ничего не мешает попросить контейнер запустить исполняемый файл `bash` — оболочку для терминала, также называемую шеллом (shell). В шелле можно тренироваться запускать команды из раздела про Linux.
```bash
docker run --rm -it gauss:1.0 /bin/bash
```
>[!NOTE] Мы указываем *абсолютный* путь к bash, а лежит он по адресу `/bin/`.
`-it` значит i[nteractive] t[erminal]. Если запускать по отдельности, то ничего не сработает, потому что терминалу нужен специальный поток `stdin`. Про него поговорим в модуле про Linux. 

Если вы хотите создать контейнер для дальнейшего использования, опустите флаг `--rm`. Тогда после завершения контейнера (например, командой `exit` в bash) вы сможете увидеть остановленный контейнер с помощью команды:
```bash
docker ps -a
```
`-a` значит a[ll]. Не указав этот флаг, вы получите список активно запущенных (но не остановленных) контейнеров.

Запустить остановленный контейнер можно командой:
```bash
docker start -ai --name my-container
```
`-ai` значит a[ttach] i[nteractive]. Вы присоединяетесь (attach) к той программе, которую создавали через `-it`. Если это был `bash`, то вас пустит в терминал контейнера. 

## Volume
Когда мы удаляем контейнер, мы удаляем данные вместе с ним. Если вы хотите прикрепить настоящую папку в контейнер (чтобы данные пережили удаление контейнера), это можно сделать командой:
```bash
docker run <остальные аргументы> -v gauss-data:/gauss-data:ro
```
Первый аргумент перед двоеточием — путь к директории на вашей машине, а `/gauss-data` — ее имя в контейнере. `ro` означает "только чтение". Если опустить аргумент, контейнер получит права записывать в эту папку.

# Залезаем в контейнер через IDE
Наверняка у вас есть любимая среда разработки или IDE. Поэтому умные люди придумали, как облегчить нам жизнь при работе с контейнерами. 

Если у вас Visual Studio Code, то можно установить расширения Dev Containers и Docker. После этого залезть в ваш контейнер можно, нажав <kbd>Ctrl</kbd> + <kbd>Shift</kbd> + <kbd>P</kbd> (или <kbd>Cmd</kbd> вместо <kbd>Ctrl</kbd>, если вы на Mac) и набрав Attach to running container. После двойного нажатия <kbd>Enter</kbd> вы попадёте внутрь контейнера.
